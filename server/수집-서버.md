# 수집 서버

## 1.1 개요

### 기능 설명

GeoVerse 서버 중 **수집 서버**는 현장에서 올라오는 센서 측정값을 받아 저장하고 집계하는 역할을 한다. 화면에 실시간으로 값을 내려보내고, 기준을 벗어난 값이 감지되면 알람을 발생시킨다.

데이터가 들어와서 나가기까지의 흐름은 다음과 같다.

```
현장 센서 ─┬→ 형식 판별 → 해석 ─┬→ 실시간 저장 → (주기적) 집계 저장
           │                     ├→ 실시간 전송 (대시보드)
LoRa 장비 ─┘                     └→ 알람 판정 → 문자 통지 + 이력 저장
```

이 서버는 화면 요청에 응답하는 조회 기능을 제공하지 않는다. 저장된 데이터의 조회는 **센서 조회 서버**가, 현장·센서 정보와 임계값 설정은 **관리 서버**가 담당한다.

### 기본 정보

| 항목 | 내용 |
| --- | --- |
| 기본 포트 | 3003 |
| 실시간 전송 | 같은 포트에서 제공 |
| 상시 동작 | 서버가 켜져 있는 동안 계속 데이터를 받는다 |

상태 확인 기능(`GET /health`)을 제공하며, 관리 서버에서 임계값이 변경되면 이를 통보받아 알람 기준을 갱신한다.

### 예외 처리

- 데이터베이스 연결에 실패하면 서버는 계속 동작하지만 알람 기준을 읽을 수 없어 알람이 발생하지 않는다.
- 저장 공간 초기화에 실패해도 데이터가 처음 들어오는 시점에 자동으로 만들어진다.

## 1.2 연동 대상

### 기능 설명

수집 서버는 아래 대상과 연동한다.

| 연동 대상 | 용도 |
| --- | --- |
| MQTT 브로커 | 현장 센서 데이터 수신 |
| Redis | 실시간 측정값 저장, 알람 재알림 대기 상태 관리 |
| InfluxDB | 집계 데이터 저장, 알람 이력 저장 |
| PostgreSQL | 알람 기준값, 센서 이름, 현장 연락처 조회 |
| 문자 발송 서비스 | 알람 및 해제 통지 |
| 웹 대시보드 | 실시간 데이터 전송 |

### 예외 처리

- 브로커 연결이 끊기면 자동으로 재연결을 시도하며, 그동안 들어온 데이터는 받지 못한다.
- 문자 발송에 실패해도 데이터 수집과 저장은 정상적으로 계속된다.

## 1.3 데이터 수신

### 기능 설명

현장 데이터는 **두 가지 경로**로 들어온다. 대부분의 센서는 MQTT 브로커를 통해 들어오고, LoRa 장비는 별도 요청으로 직접 전달한다.

### 수신 경로

MQTT로 구독하는 대상은 다음과 같다.

| 구분 | 내용 |
| --- | --- |
| 집계·고주파 데이터 | 이미 통계 처리가 된 상태로 올라오는 데이터 |
| geocus900 계열 센서 | 현장에 설치된 다채널 계측 장비 |
| catM1 계열 센서 | 이동통신망을 사용하는 계측 장비 |

LoRa 장비 데이터는 다음 요청으로 받는다.

```text
POST /api/lora
```

| 항목 | 필수 | 설명 |
| --- | --- | --- |
| key | 필수 | 장비 식별자. 저장 공간 이름에 사용된다 |
| data.time | 필수 | 측정 시각 |
| data.val01 ~ val04 | 선택 | 측정값 |
| isGdms | 선택 | GDMS 형식으로 처리할지 여부 |

### 처리 절차

1. 브로커에서 메시지를 받아 형식을 확인한다.
2. 센서 종류에 따라 처리 경로를 나눈다.
3. LoRa 요청은 장비 식별자와 측정 시각을 확인한 뒤 바로 저장한다.
4. 일반 LoRa 데이터는 측정값 4개를 각각 저장하고 실시간 전송까지 진행한다.
5. GDMS 형식은 받은 내용을 그대로 한 건 저장한다.

### 예외 처리

- 형식이 잘못된 메시지는 기록만 남기고 넘어간다. 이후 들어오는 데이터 처리에는 영향을 주지 않는다.
- LoRa 요청에서 장비 식별자나 측정 시각이 빠지면 요청을 거부한다.
- 브로커 연결이 끊어졌다 복구되면 재연결 횟수와 중단 시간이 기록된다.

## 1.4 데이터 해석

### 기능 설명

센서마다 보내는 데이터 형태가 달라서, **들어온 내용을 보고 형식을 판별한 뒤 공통 구조로 바꾼다.** 이후 단계는 모두 이 공통 구조를 사용한다.

### 처리 규칙

| 들어온 형태 | 처리 방식 |
| --- | --- |
| 측정값이 목록으로 들어온 경우 | 여러 채널을 한 번에 담은 형식으로 해석 |
| 채널이 하나만 지정된 경우 | 이미 통계 처리된 집계·고주파 데이터로 해석 |
| 채널이 여러 개인 경우 | 일반 다채널 센서 데이터로 해석 |

일부 레거시 센서는 별도 경로로 처리한다. 이 중 한 종류는 두 개의 채널을 하나로 합쳐서 다룬다.

측정 시각은 한국 시간 기준 문자열로 들어오며, 저장할 때는 표준 시각으로 변환한다.

### 예외 처리

- 해석할 수 없는 데이터는 이후 단계로 넘기지 않는다.
- 숫자가 아닌 측정값은 저장과 알람 판정에서 제외된다.

---

## 1.5 실시간 저장

### 기능 설명

해석된 측정값을 **센서와 채널별로 시각순 목록에 저장**한다. 이 데이터가 대시보드의 실시간 표시와 최근 구간 조회에 사용된다.

### 처리 절차

1. 측정 시각을 기준값으로 삼아 센서·채널별 목록에 값을 넣는다.
2. 같은 저장 동작에서 24시간이 지난 데이터를 함께 삭제한다.

저장과 정리가 한 번에 처리되므로 오래된 데이터가 쌓이지 않는다.

### 표시 규칙

이미 통계 처리가 끝난 집계·고주파 데이터는 실시간 저장소를 거치지 않고 곧바로 집계 저장소에 기록된다.

### 예외 처리

- 저장에 실패해도 오류를 기록하고 다음 데이터 처리를 계속한다.

---

## 1.6 실시간 전송

### 기능 설명

새 측정값이 들어올 때마다 **대시보드에 즉시 전달**한다. 화면을 새로 열었을 때는 모든 센서의 최신값을 한 번에 받아 바로 값이 채워지도록 한다.

### 처리 절차

1. 대시보드가 접속하면 보관 중인 모든 센서의 최신값을 한 번 전송한다.
2. 이후 새 데이터가 들어올 때마다 해당 센서의 값을 전송한다.
3. 최신값은 항목별로 시각을 비교해 더 최근 값만 갱신한다.

### 표시 규칙

센서 하나가 여러 채널을 가지고 있고 채널마다 도착 시각이 다를 수 있으므로, 최신값은 **항목 단위로 따로 관리**한다. 한 채널의 값이 늦게 들어와도 다른 채널의 최신값이 사라지지 않는다.

### 예외 처리

- 대시보드 접속이 끊겨도 데이터 수집과 저장은 영향을 받지 않는다.

---

## 1.7 집계 저장

### 기능 설명

실시간 데이터를 **일정 시간 단위로 모아 평균·최대·최소를 계산해 보관**한다. 기간별 조회와 장기 보관에 사용한다.

### 처리 주기

정해진 시각마다 자동으로 실행되는 작업이 세 가지 있다.

| 작업 | 실행 시점 | 처리 내용 |
| --- | --- | --- |
| 10분 집계 | 10분마다 | 최근 10분 실시간 데이터를 모아 저장 |
| 시간별 집계 | 매시 정해진 분 | 10분 집계를 1시간 단위로 합산 |
| 일별 집계 | 매일 자정 이후 | 시간별 집계를 1일 단위로 합산 |

10분 집계는 정확히 10분마다가 아니라 **몇 분 늦춰서 실행**한다. 늦게 도착한 데이터까지 포함시키기 위한 것이다.

### 표시 규칙

저장 공간은 센서 종류에 따라 나뉜다.

| 센서 구분 | 저장 공간 구성 |
| --- | --- |
| 일반 센서 | 센서·채널·집계단위마다 따로 |
| 레거시 센서 | 센서마다 하나. 채널은 내부 표시로 구분 |
| LoRa 장비 | 장비마다 하나 |

저장 공간은 서버가 시작될 때 설정 기준으로 미리 만들어지고, 설정에 없는 센서가 들어오면 저장 시점에 자동으로 만들어진다. 보관 기간은 집계 단위별로 다르게 적용된다.

집계·고주파 데이터는 같은 시각의 같은 항목이 이미 저장되어 있으면 다시 쓰지 않는다.

### 예외 처리

- 처리할 데이터가 없으면 아무 작업도 하지 않는다.
- 집계 중 오류가 발생하면 기록을 남기고 다음 주기에 다시 시도한다.

## 1.8 알람 판정

### 기능 설명

들어온 측정값이 **관리 서버에서 설정한 기준을 벗어났는지 확인**한다. 순간적으로 튀는 값에 반응하지 않도록 일정 시간 이상 기준을 벗어난 상태가 유지될 때만 알람으로 판정한다.

### 처리 절차

측정값 하나마다 다음 순서로 확인한다.

1. **계산식 적용** — 화면 설정에 계산식이 있으면 적용한 값으로 판정한다.
2. **발송 시간대 확인** — 정해진 시간대 밖이면 판정하지 않는다.
3. **기준값 조회** — 설정된 기준이 없으면 넘어간다.
4. **단계 판정** — 높은 단계부터 확인해 해당하는 단계를 정한다.
5. **재알림 대기 확인** — 최근에 같은 알람을 보냈으면 넘어간다.
6. **지속 시간 확인** — 설정 시간만큼 유지되면 통지한다.

지속 시간과 해제 시간은 항목별로 관리 서버에서 설정한 값을 사용한다.

### 처리 규칙

기준값 설정 방식에 따라 판정이 달라진다.

| 설정 | 알람으로 보는 경우 |
| --- | --- |
| 상한만 설정 | 상한을 넘었을 때 |
| 하한만 설정 | 하한보다 낮을 때 |
| 양방향 설정 | 설정 범위를 벗어났을 때 |

단계는 3단계, 2단계, 1단계 순으로 확인하며 **가장 높은 단계가 적용**된다.

시간과 관련된 동작은 다음과 같다.

| 상황 | 동작 |
| --- | --- |
| 기준 초과 시작 | 지속 시간을 세기 시작한다 |
| 지속 중 정상값 복귀 | 세던 시간을 취소하고 통지하지 않는다 |
| 지속 중 단계 상승 | 시간을 다시 세기 시작한다 |
| 지속 시간 충족 | 통지하고 재알림 대기를 시작한다 |
| 대기 중 단계 상승 | 대기를 해제하고 즉시 통지한다 |
| 정상 상태 지속 | 해제 통지를 보낸다 |

알람 발송 시간대는 **오전 6시부터 오후 6시까지**다. 야간 발송을 막기 위한 설정이다.

### 예외 처리

- 기준값 설정이 없는 항목은 알람 판정 대상이 아니다.
- 이전에 경보가 발생하지 않았다면 해제 통지를 보내지 않는다.
- 관리 서버에서 기준값을 변경하면 통보를 받아 즉시 새 기준을 적용한다.

## 1.9 알람 통지

### 기능 설명

알람으로 판정된 내용을 **담당자에게 문자로 알린다.** 상황이 정상으로 돌아오면 해제 문자를 보낸다.

### 처리 규칙

통지 대상은 현장에 등록된 단계별 연락처를 사용하며, 단계와 연락처는 하나씩 대응한다. 여러 단계에 중복 발송하지 않는다.

| 알람 단계 | 통지 대상 | 문자 표기 |
| --- | --- | --- |
| 1단계 | 1차 연락처 | 주의 |
| 2단계 | 2차 연락처 | 경고 |
| 3단계 | 3차 연락처 | 위험 |

문자에는 단계 표기, 센서 이름과 현장 이름, 측정 항목과 측정값, 벗어난 기준, 발생 시각이 담긴다. 센서 이름과 항목 이름은 관리 서버에 등록된 이름을 사용한다.

해제 문자는 **경보를 받았던 연락처에만** 발송하며, 해당 항목이 정상으로 돌아왔음을 알린다.

### 예외 처리

- 현장에 연락처가 등록되어 있지 않으면 발송하지 않는다.
- 문자 발송 서비스 인증 정보가 없으면 발송하지 않는다.
- 발송이 실패해도 데이터 수집과 저장은 정상적으로 계속된다.

---

## 1.10 알람 이력 저장

### 기능 설명

발송된 경보와 해제 내역을 **이력으로 남긴다.** 관리 화면의 알람 이력 조회가 이 기록을 사용한다.

### 표시 규칙

이력에는 발생 시각, 센서와 채널, 측정 항목, 측정값, 벗어난 기준, 알람 단계, 통지 대상, 발송된 문자 내용이 함께 저장된다.

보관 기간은 **90일**이다.

### 예외 처리

- 문자 발송이 실패한 경우에는 이력이 남지 않는다.
- 이력 저장 공간은 서버 시작 시 없으면 자동으로 만들어진다.

## 1.11 데이터 흐름 요약

### 처리 단계별 정리

| 단계 | 처리 내용 | 보관 위치 |
| --- | --- | --- |
| 수신 | MQTT 및 LoRa 요청으로 데이터 수신 | - |
| 해석 | 형식 판별 후 공통 구조로 변환 | - |
| 실시간 저장 | 센서·채널별 시각순 저장, 24시간 보관 | Redis |
| 실시간 전송 | 대시보드에 즉시 전달 | 메모리 |
