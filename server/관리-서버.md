# 관리 서버 — 프로그램 명세

**작성 기준**: `management/server.js`, `api.js`, `database/pg-client.js`, `database/repositories/*`, `auth-api/*`, `middleware/auth.js`, `services/token-service.js`, 도메인별 `*-api/index.js`, `backup-scheduler.js`, `redis-backup.js`

## 1. 데이터 구조와 흐름

### 1.1 요청 흐름

```mermaid
flowchart TB
    C[관리 화면] --> M1[helmet]
    M1 --> M2[cors]
    M2 --> M3[express.json]
    M3 --> M4[morgan]
    M4 --> ST["정적 이미지 제공"]
    M4 --> R["api.js 라우터"]
    R --> D1["도메인 라우터 17개"]
    D1 --> REPO[database/repositories]
    REPO --> PG[(PostgreSQL)]
    D1 -->|알람 이력| INF[(InfluxDB)]
    D1 -->|임계값 변경 통보| COL[수집 서버]
    D1 -->|토큰| RD[(Redis)]
```

미들웨어는 `helmet` → `cors` → `express.json` → `morgan` → `/images` 정적 제공 → OPTIONS 처리 순서로 등록된다. 서버 시작 시 PostgreSQL에 연결해 `initializeTables()`로 테이블·인덱스·트리거를 확인하고, 위젯 채널 캐시를 예열한 뒤 백업 스케줄러를 시작한다.

### 1.3 테이블 관계

```mermaid
erDiagram
    projects ||--o{ nodes : "project_id"
    projects ||--o{ sensor_groups : "project_id"
    projects ||--o{ sensors : "project_id"
    projects ||--o{ siblings : "project_id"
    nodes ||--o{ nodes : "ltree path"
    nodes ||--o{ folders : "node_id"
    nodes ||--o{ devices : "node_id"
    nodes ||--o{ sensor_groups : "node_id"
    folders ||--o{ devices : "folder_id"
    sensor_groups ||--o{ sensors : "group_id"
    siblings ||--o{ sensors : "sibling_id"
```

`device_types`, `sensor_types`, `sensor_widgets`, `sensor_thresholds`, `cctv_cameras`, `users`는 외래키로 연결되지 않은 독립 테이블이다.

구조는 두 계층으로 나뉜다.

| 계층 | 경로 | 용도 |
| --- | --- | --- |
| 설비 계층 | `projects` → `nodes` → `folders` → `devices` | 현장 구조와 장비 등록 |
| 표시 계층 | `projects` → `sensor_groups` → `sensors` | 화면에 보여줄 센서 구성 |

독립 테이블은 `site_code` 또는 `device_id` 문자열로 다른 테이블과 논리적으로 연결된다. 수집 서버의 알람 판정은 `sensor_thresholds`, `sensor_widgets.options`, `projects.alarm_contacts`만 읽고 `devices`나 `sensors` 테이블은 조회하지 않는다.

### 1.5 JSONB 컬럼 구조

`projects.alarm_contacts`

```json
{ "1차": ["01000000000"], "2차": [{ "name": "담당자", "phone": "01000000000" }], "3차": [] }
```

`devices.channels` — 객체 배열. 각 항목은 비어 있지 않은 `name`을 가져야 하고 이름 중복은 API에서 거부한다.

`sensor_widgets.options`

```json
{
  "parseType": "geocus",
  "deviceChannels": [{ "deviceId": "geocus900_1002_01", "channel": "ch2" }],
  "sensorList": [{
    "deviceId": "geocus900_1002_01",
    "channel": "ch2",
    "name": "표시 이름",
    "values": [{ "name": "풍속", "dataIndex": "WS", "formula": "x * 1" }]
  }],
  "cameras": [{ "id": 1 }]
}
```

`sensors.display_config` — `{ unit, decimal, chartType, color, formula }` 형태로 사용하며 갱신 시 기존 값과 병합(`||`)한다.

### 1.6 인증 흐름

```mermaid
sequenceDiagram
    participant C as 관리 화면
    participant A as auth-api
    participant P as PostgreSQL
    participant R as Redis

    C->>A: POST /api/auth/login/v2
    A->>P: users 조회
    A->>P: last_login_at 갱신
    A->>R: SET refresh_token:{userId} (7일)
    A-->>C: accessToken(15분) + refreshToken(7일)

    C->>A: POST /api/auth/refresh
    A->>R: GET refresh_token:{userId} 비교
    A-->>C: 새 토큰 쌍

    C->>A: POST /api/auth/logout
    A->>R: SET blacklist:{token} (남은 만료까지)
    A->>R: DEL refresh_token:{userId}
```

| Redis 키 | 자료형 | 값 | TTL |
| --- | --- | --- | --- |
| `refresh_token:{userId}` | STRING | 갱신 토큰 | 7일 |
| `blacklist:{token}` | STRING | `blacklisted` | 토큰 남은 만료 시간 |

토큰 검증 미들웨어는 `GET /api/auth/verify`, `GET /api/auth/me`에 `optionalAuthenticateToken`으로 적용된다.

### 1.7 임계값 변경 통보

```mermaid
flowchart LR
    A["POST /api/thresholds/:siteCode"] --> B["upsertBatch"]
    B --> C["수집 서버 캐시 초기화 요청"]
    C -->|성공| D["응답 반환"]
    C -->|실패| E["경고 로그 후 응답 반환"]
```

| 항목 | 값 |
| --- | --- |
| 호출 함수 | `threshold-api/index.js` `clearCollectorCache()` |
| 대상 | `{collector.url}/internal/clear-threshold-cache` |
| 메서드·본문 | `POST`, 빈 JSON |
| 타임아웃 | 3000ms |
| 실패 처리 | 경고만 남기고 API는 성공 응답 |

호출 시점은 임계값 일괄 저장(`POST /:siteCode`)과 장비 단위 삭제(`DELETE /device/:deviceId`) 직후다.

### 1.8 백업 스케줄러

```mermaid
flowchart TD
    A["서버 시작 startBackupScheduler"] --> B["Redis 연결"]
    B --> C["매일 00:30 크론"]
    C --> D["getSensorDataCount"]
    D --> E["외부 백업 API로 대상 구간 요청"]
    E -->|성공| F["cleanupOldData 구간 삭제"]
    E -->|실패| G["중단, 데이터 유지"]
```

대상 구간은 이틀 전 하루 전체(`00:00:00.000` ~ `23:59:59.999`)이고, 외부 백업 API가 성공을 반환한 경우에만 `timeseries:{sensorId}:*` 키에서 해당 점수 범위를 삭제한다. 대상 센서 목록은 코드에 고정되어 있다.

## 4. 구현 시 주의사항

1. **라우트에 인증이 걸려 있지 않다.** `authenticateToken`, `requireRole`, `requireAdmin`은 정의되어 있으나 `/api/*`에 적용되지 않았다. 접근 제어는 네트워크 수준에서 관리해야 한다.
2. **`sensor_thresholds.cooldown` 단위 차이.** 테이블 기본값은 1800이지만 수집 서버는 이 값을 분으로 해석한다. 저장 시 분 단위로 넣어야 한다.
3. **위젯 캐시는 쓰기 시 갱신되지 않는다.** `POST`/`PUT`/`DELETE` 후 `widgetChannelCache`를 다시 채우지 않으므로 조회 경로의 TTL 만료나 재시작에 의존한다.
4. **프로젝트 생성은 파티션 생성을 포함한다.** `sensor_groups`, `sensors`가 `project_id` 기준 LIST 파티션이므로 파티션 없이 데이터를 넣으면 실패한다.
5. **노드 이동은 하위 경로를 함께 갱신해야 한다.** `node-api`가 트랜잭션 안에서 하위 `path`를 직접 수정하며, 리포지토리의 `moveTo`는 사용하지 않는다.
6. **임계값 저장 후 통보 실패는 무시된다.** 수집 서버가 내려가 있으면 캐시가 갱신되지 않아 새 기준이 즉시 반영되지 않는다.
7. **백업 대상 센서와 수신자가 코드에 고정되어 있다.** 운영 현장을 추가할 때 코드 수정이 필요하다.
8. **`devices.device_type`과 카탈로그 사이에 외래키가 없다.** 카탈로그에서 항목을 지워도 장비 행은 그대로 남는다.
