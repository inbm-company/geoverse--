# 센서 조회 서버

## 1.1 개요

### 기능 설명

GeoVerse 서버 중 **센서 조회 서버**는 수집된 데이터를 화면에 보여 주기 위해 조회 결과를 만들어 내보내는 역할을 한다. 실시간 값과 기간별 집계 값을 나누어 제공하고, 측정값을 수동으로 고치는 기능과 현장 날씨를 알려 주는 기능을 함께 담당한다.

- 최근 몇 시간 이내의 값은 Redis에서 바로 읽어 내보낸다.
- 며칠·몇 달 단위의 값은 InfluxDB의 집계 데이터에서 읽어 내보낸다.
- 잘못 들어간 집계 값을 파일 기준으로 다시 써 넣을 수 있다. (상세 조회 화면의 엑셀 업로드가 이 기능을 사용한다.)
- 현장 좌표를 받아 기상청 날씨를 대신 조회해 준다.

데이터를 직접 수집하거나 알람을 판단하지는 않는다. 수집은 **수집 서버**가, 현장·센서 정보 관리는 **관리 서버**가 담당한다.

### 기본 정보

| 항목 | 내용 |
| --- | --- |
| 기본 포트 | 3002 |
| 사용 대상 | 웹 대시보드 및 상세 조회 화면 |
| 접근 제한 | 별도 로그인 절차 없음. 내부망 전용 |

### 예외 처리

- 서버가 막 켜진 직후 짧은 시간 동안은 데이터베이스 준비가 끝나지 않아 조회가 실패할 수 있다.
- 내부망 밖에 노출하면 누구나 측정값을 고칠 수 있으므로 외부 공개를 하지 않는다.

## 1.2 연동 대상

### 기능 설명

이 서버는 스스로 데이터를 보관하지 않고, 아래 세 곳에서 값을 가져오거나 써 넣는다.

| 연동 대상 | 용도 |
| --- | --- |
| Redis | 최근 실시간 측정값 읽기 |
| InfluxDB | 기간별 집계값 읽기, 보정값 쓰기 |
| 기상청 날씨 API | 현재 날씨와 하늘상태 조회 |

### 예외 처리

- Redis 연결이 끊기면 실시간 조회만 실패하고, 기간별 조회는 계속 동작한다.
- 기상청 응답이 늦으면 10초 후 요청을 끊고 오류를 반환한다.

## 1.3 실시간 조회

### 기능 설명

최근 몇 시간 동안의 측정값을 **원본과 요약 두 가지로 나누어** 내보낸다. 화면에서 최신 구간은 값이 찍히는 대로 보여 주고, 그 이전 구간은 일정 간격으로 묶은 평균·최소·최대로 보여 주기 위한 구분이다.

### 요청 형식

```text
GET /api/sensors/realtime
```

| 항목 | 필수 | 기본값 | 설명 |
| --- | --- | --- | --- |
| sensorId | 필수 | - | 조회할 센서 |
| hours | 선택 | 1 | 현재 시각 기준 몇 시간 전까지 |
| aggregateSeconds | 선택 | 60 | 요약을 만드는 시간 간격(초) |
| channel | 선택 | 전체 | 특정 채널만 볼 때 지정 |
| types | 선택 | avg | avg, min, max 중 필요한 것 |

### 처리 절차

1. 현재 시각에서 요청한 시간만큼 거슬러 올라간 구간을 정한다.
2. 해당 구간의 값을 Redis에서 모두 읽어 시간순으로 정렬한다.
3. 가장 최근 구간의 값은 손대지 않고 원본 그대로 내보낸다.
4. 그 이전 값들은 지정한 간격으로 묶어 평균·최소·최대를 계산한다.

### 응답 규칙

| 영역 | 내용 |
| --- | --- |
| realtime | 최근 구간의 원본 측정값 목록 |
| aggregated | 그 이전 구간의 요약값. 요청한 종류(avg/min/max)만 포함 |
| window | 조회 구간과 실시간·요약의 경계 시각 |

### 예외 처리

- 센서 지정이 없으면 요청을 거부한다.
- 해당 구간에 값이 하나도 없으면 오류가 아니라 빈 목록을 내보낸다.

## 1.4 기간별 조회

### 기능 설명

지정한 시작·종료 시각 사이의 **집계된 측정값**을 내보낸다. 상세 조회 화면의 차트와 기록 표가 이 결과를 사용한다.

### 요청 형식

```text
GET /api/sensors/range
```

| 항목 | 필수 | 기본값 | 설명 |
| --- | --- | --- | --- |
| sensorId | 필수 | - | 조회할 센서 |
| start / end | 필수 | - | 조회 구간의 시작·종료 시각 |
| channel | 조건부 | - | 일반 센서는 필수, LoRa 센서는 생략 |
| timeUnit | 선택 | 10m | 10분·1시간·1일 중 집계 단위 |
| types | 선택 | avg | 평균·최소·최대 중 필요한 것 |
| isFft | 선택 | false | 고주파 센서의 채널 규칙 적용 여부 |
| isTest | 선택 | false | 테스트용 데이터 조회 여부 |
| isLora | 선택 | false | LoRa 센서 조회 여부 |

### 처리 절차

1. 센서 종류를 판별해 어느 저장 공간을 볼지 정한다.
2. 집계 단위에 맞는 데이터를 지정 구간만큼 읽는다.
3. 시각별로 묶고 요청한 통계 종류만 남겨 내보낸다.

### 표시 규칙

| 요청 값 | 실제 조회되는 값 |
| --- | --- |
| avg | 평균값 |
| min / max | 최소값 / 최대값 |

고주파 센서는 채널 번호가 저장 시점에 다르게 기록되므로, 조회할 때 자동으로 맞춰 준다.

### 예외 처리

- 센서나 구간이 빠지면 요청을 거부한다.
- 일반 센서인데 채널을 지정하지 않으면 요청을 거부한다.
- 조회 대상 저장 공간이 없으면 오류를 반환한다.

## 1.5 측정값 수동 보정

### 기능 설명

이미 저장된 **집계 측정값을 사람이 직접 고쳐 써 넣는** 기능이다. 상세 조회 화면의 엑셀 업로드가 최종적으로 이 기능을 사용한다. 현장 보정이나 잘못 들어간 값의 정정에 쓴다.

실시간 데이터와 알람에는 영향을 주지 않는다. 이미 지나간 집계 값만 바뀐다.

### 요청 형식

```text
POST /api/sensors/overwrite
```

| 항목 | 필수 | 설명 |
| --- | --- | --- |
| isTest | 필수 | 실제 데이터인지 테스트 데이터인지 구분 |
| data | 필수 | 고칠 측정값 목록 |
| isFFT | 선택 | 고주파 센서 여부 |
| isLora | 선택 | LoRa 센서 여부 |
| isGdms | 선택 | GDMS 형식 데이터 여부 |

목록의 각 항목은 센서, 채널, 시각, 측정값으로 구성한다. 측정값에는 평균이 반드시 있어야 하고, 최대·최소가 없으면 평균값으로 채운다.

### 처리 절차

1. 항목별로 형식이 올바른지 확인한다.
2. 시각을 10분 단위로 맞춘다.
3. 저장할 공간이 없으면 새로 만든다. 이때 보관 기간은 2년으로 설정된다.
4. 값을 써 넣고 처리 건수를 집계한다.

### 응답 규칙

| 상황 | 결과 |
| --- | --- |
| 전부 성공 | 성공으로 응답하며 처리 건수를 함께 알려 준다 |
| 일부 성공 | 성공·실패 건수와 실패 사유를 항목별로 알려 준다 |
| 전부 실패 | 실패로 응답한다 |

### 예외 처리

- 형식이 맞지 않는 항목은 건너뛰고 나머지는 계속 처리한다.
- 잘못된 항목의 위치와 사유를 응답에 남긴다.
- 테스트 구분을 잘못 지정하면 운영 데이터가 바뀔 수 있으므로 실행 전 반드시 확인한다.

## 1.6 날씨 조회

### 기능 설명

현장 좌표를 받아 **현재 날씨**를 알려 준다. 대시보드 상단의 날씨 표시에 사용한다.

### 요청 형식

```text
POST /api/weather
```

| 항목 | 필수 | 설명 |
| --- | --- | --- |
| lat | 필수 | 위도 |
| lon | 필수 | 경도 |

### 처리 절차

1. 위경도를 기상청이 쓰는 격자 좌표로 바꾼다.
2. 같은 격자의 최근 조회 결과가 있으면 그대로 사용한다.
3. 없으면 기상청에서 기온·강수량·습도·풍속·강수형태를 가져온다.
4. 하늘상태는 별도 조회로 가져와 합친다.
5. 결과를 30분간 보관한다.

### 표시 규칙

| 상황 | 표시되는 날씨 |
| --- | --- |
| 비·눈이 오는 중 | 강수형태(비, 눈, 소나기 등) |
| 강수 없음 | 하늘상태(맑음, 구름많음, 흐림) |

### 예외 처리

- 좌표가 숫자가 아니면 요청을 거부한다.
- 하늘상태 조회만 실패하면 나머지 날씨는 정상적으로 내보낸다.
- 기상청 응답이 없거나 늦으면 오류를 반환한다.

## 1.7 데이터 보관 구조

### 기능 설명

조회 결과가 어디에서 나오는지에 대한 설명이다.

| 구분 | 보관 위치 | 보관 형태 |
| --- | --- | --- |
| 실시간 값 | Redis | 센서와 채널별로 시각순 목록 |
| 집계 값 | InfluxDB | 센서·채널·집계단위별 저장 공간 |

### 표시 규칙

| 센서 구분 | 저장 공간 구성 |
| --- | --- |
| 일반 센서 | 센서와 채널마다 저장 공간이 나뉜다 |
| LoRa 센서 | 센서 하나에 저장 공간 하나. 채널 구분이 없다 |
| 레거시 센서 3종 | 센서 하나에 저장 공간 하나. 채널은 내부 표시로 구분한다 |

레거시 센서 3종: `geocus900_1001_01`, `geocus900_1002_01`, `geocus900_1003_01`

집계 단위는 10분·1시간·1일 세 가지이고, 테스트 데이터는 실제 데이터와 분리해서 보관한다.

## 1.8 기능별 특성 요약

| 기능 | 데이터 출처 | 운영 데이터 변경 |
| --- | --- | --- |
| 실시간 조회 | Redis | 없음 |
| 기간별 조회 | InfluxDB | 없음 |
| 수동 보정 | InfluxDB | **있음** |
| 날씨 조회 | 기상청 | 없음 |

조회 기능은 값을 읽기만 하지만, 수동 보정은 저장된 값을 직접 바꾼다. 운영 중 주의가 필요한 기능은 수동 보정 하나다.
