# 위젯 카드 통일 표시 구조(displayItems) — 프로그램 명세

**작성 기준**: `sensorWidgetItemsUtils.js`, `widgetGridCardItemUtils.js`, `gdmsWidgetCalculations.js`

***

## 1. 데이터 구조와 흐름

### 1.1 핵심 원칙

> `if parseType == ...` 분기는 **데이터 관리단(표시 구조 생성기) 안에서만** 존재한다. 컴포넌트와 `WidgetGridCardContent`에는 parseType 분기를 두지 않는다.

### 1.2 전체 구조

```
데이터 관리단
  useWidgetGridCardData (range + socket 합류)
    → getSensorWidgetDisplayItems(widget, rowsByChannel)   ← parseType 분기 유일 지점
        ├─ gdms   → 축별 총합 아이템
        ├─ lora   → 채널별 아이템
        ├─ MQTT→ device+channel 묶음 아이템
        └─ HTTP    → 채널별 아이템
    → widgetData.displayItems (통일 구조)

컴포넌트 (parseType 모름, 계산 없음)
  게이지      : displayItems를 groupKey로 묶어 카드 렌더 (아이템 2개↑ = 체이닝 A | B)
  리스트      : displayItems 행 렌더
  바차트/스택  : displayItems의 value + threshold
  저빈도차트   : displayItems의 series
```

### 1.3 DisplayItem 계약

데이터 관리단이 산출하는 유일한 표시 구조다. 뷰 중립 이름을 쓴다(게이지 전용 아님).

```javascript
widgetData.displayItems: DisplayItem[]

DisplayItem = {
  key,          // 렌더 안정 키 (위젯 내 유일)
  groupKey,     // 묶음 키 — 게이지 체이닝/카드 그룹 기준
  title,        // 카드/센서 제목
  label,        // 아이템 이름표 (예: A축 / B축)
  value,        // 현재값 (range + socket 합류 완료값)
  unit,         // 표시 단위
  decimals,     // 소수 자리수 (있으면)
  threshold,    // 기준치
  status,       // 정상/주의/경고 등 상태
  tone,         // 상태 톤
  timestamp,    // 최신 시각
  series,       // 시계열 [{ timestamp, value }] — 차트용
}
```

`series`는 **parseType 상관없이 항상 생성**한다. 어떤 뷰가 붙을지 모르고 생성 부담이 크지 않다.

### 1.4 뷰별 소비 방식 (parseType 몰라도 됨)

| 뷰                                   | 소비                                                   |
| ----------------------------------- | ---------------------------------------------------- |
| 리스트(`SensorListGauge`)              | `displayItems`를 행으로 렌더                               |
| 게이지(`SensorGauge` / `ChainedGauge`) | `groupKey`로 묶어 카드 구성. 아이템 1개 = 단일, 2개↑ = 체이닝(A \| B) |
| 바차트/스택                              | `value` + `threshold`                                |
| 저빈도차트                               | `series`                                             |

### 1.5 parseType별 매핑 (분기는 여기 한 곳)

| parseType   | 카드 단위(groupKey)   | 아이템                    |
| ----------- | ----------------- | ---------------------- |
| gdms        | 위젯 1개 = 카드 1개     | 축(A/B) **총합** = 아이템 N개 |
| lora / HTTP | 채널마다 카드           | 채널당 1아이템               |
| MQTT        | device+channel 묶음 | 묶음당 N아이템               |

* `displayValues` / `chartValues`로 나뉘어 있던 산출은 `displayItems` 하나로 통합돼 있다.
* 그룹핑(체이닝)은 데이터가 아니라 **게이지 렌더 시 `groupKey`로 묶는 순수 헬퍼**로 처리한다.

### 1.6 이 구조를 쓰는 이유

이전에는 카드 하나를 그리는 데 세 곳에서 각각 값을 파생하고 마지막에 문자열 key로 결합했다.

| 파생           | 위치                                                                                          | 산출                                       |
| ------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 1. 값         | `getSensorWidgetValues`                                                                     | `displayValues` (값 리스트)                  |
| 2. 렌더 config | `getWidgetGaugeConfigs` / `getWidgetSensorListGaugeSensors` / `getWidgetValueBarChartProps` | options 재해석 config                       |
| 3. 값 재계산     | 컴포넌트 `useGaugeData`                                                                         | 소켓 재구독 + 값 재계산, 데이터층 값은 override 패치로만 반영 |
| 접착           | `buildValueByKey`                                                                           | `deviceId-channel-dataKey` 문자열 매칭        |

이 방식에는 세 가지 문제가 있었다.

* 데이터 관리단이 **값 리스트까지만** 만들고, 컴포넌트가 쓸 **렌더 구조(카드/아이템/그룹)** 는 만들지 않았다.
* 컴포넌트가 `useGaugeData`로 값을 다시 계산해 순수 표시형이 아니었다. parseType 특수 처리가 컴포넌트로 새어 나왔다.
* 파생1·2를 key로 접착하는데, GDMS 총합처럼 `deviceId` / `channel` / `dataKey`가 없는 값은 매칭이 불가능해 결합이 깨졌다.

`displayItems`는 이 세 파생을 한 곳으로 합쳐 key 접착 자체를 없앤 구조다.

## 2. GDMS 데이터 구조 해부

실제 DB 위젯 옵션과 계산 코드를 대조한 결과다. 사이트 6000 위젯(140/144/148) 기준이며, 지중경사계·도상침하계·내공변위계가 모두 같은 옵션 구조를 쓴다.

### 2.1 옵션(입력) 3층

| 층      | 필드                     | 의미                                           |
| ------ | ---------------------- | -------------------------------------------- |
| 위젯     | `parseType`            | 계산기 선택 (예: `gdms`) — 시스템 고정값                 |
| 위젯     | `values[]`             | **축 정의 = 라벨 + dataIndex** (A축→`1`, B축→`0`)   |
| 위젯     | `unit`                 | 표시 단위 (`mm`)                                 |
| 채널(깊이) | `sensorList[]`         | 채널 1개 = 깊이 1개 (ch1\~chN)                     |
| 축      | `sensorList[].items[]` | 채널 안 축별 계산식 (`dataIndex`, `formula`, `Zero`) |

* "축이 몇 개고 이름이 뭔지"는 `values[]`에 있다.
* "각 축을 어떻게 계산하는지"는 `sensorList[].items[]`의 `formula` + `dataIndex`에 있다.
* 이 둘을 **`dataIndex`로 연결**한다.

### 2.2 실측 데이터 = 매트릭스(깊이 × 축)

* 실제 값은 `row.fields.gdms.data` 매트릭스다. `parseGdmsMatrix`가 파싱한다.
* `matrix[sensorIndex]` = 깊이(채널 순서), `matrix[..][dataIndex]` = 축(A/B).
* GDMS는 **디바이스 1개 응답에 전체 매트릭스(모든 깊이)** 가 담긴다. range 조회도 디바이스 단위(`buildLoraGdmsDeviceRangeJobs`, sensorList의 deviceId 사용)이며, 채널별 rowKey는 같은 매트릭스를 공유하고 snapshot이 `sensorIndex`로 깊이를 고른다.

### 2.3 계산 경로

* `buildGdmsWidgetSnapshot` → 깊이×축 개별값
* `buildGdmsWidgetTotals` → 축별 합산("총합", 예: A | B)

### 2.4 축 식별 규칙

* 축의 이름·개수·순서는 **`values[]`를 `dataIndex`로 매칭**해서 만든다(`values` 배열 순서 그대로 사용).
* `sensorList[].items[].name` / `columnName`은 센서 컬럼명이라 축 구분용이 아니다. 축 묶음 기준으로 쓰지 않는다.

### 2.5 참고 (동작에 영향 없음)

* `rodLength`(한글키 `로드길이`)는 계산식 계수(지중경사계 로드 길이)다. `formulaExample`의 `${로드길이}` 토큰에 치환되어 각도(sin)를 변위(mm)로 환산한다.
* GDMS 디바이스는 LoRa로 전송될 수 있어 `deviceId`에 `lora_`가 붙거나 안 붙는다. 그러므로 **디바이스 이름이 아니라 `parseType`으로만 분기**한다.
* `gdmsAccumulateDirection`(`ltr` / `rtl`)은 상세 누적 테이블 방향이며 게이지 표시와 무관하다.
* `gdmsChartOption`(`vertical` / `horizontal` / `semicircle`)은 상세 드로어 프로파일 차트 종류이며 `displayItems` 산출과 무관하다. 상세는 [19-위젯-그리드-상세-드로어.md](19-%EC%9C%84%EC%A0%AF-%EA%B7%B8%EB%A6%AC%EB%93%9C-%EC%83%81%EC%84%B8-%EB%93%9C%EB%A1%9C%EC%96%B4.md)를 본다.

## 4. 사용 컴포넌트 설명

### 4.1 컴포넌트 계약

* 모든 뷰 컴포넌트는 `displayItems`만 소비한다. 컴포넌트 안에서 값을 계산하지 않는다.
* `ChainedGauge` / `SensorGauge` / `SensorListGauge`는 `useGaugeData`에 의존하지 않고, 값이 채워진 아이템을 받아 렌더만 한다.
* key 접착(`buildValueByKey`)은 게이지 경로에서 쓰지 않는다. 바차트 threshold 매칭 등 남은 용도에만 쓴다.
* parseType 분기는 `WidgetGridCardContent`와 개별 컴포넌트에 두지 않는다. 데이터 관리단으로 수렴한다.
* `useGaugeData`는 레거시 센서보드(`SensorMonitoringBoard`) 경로에만 남는다. 위젯 그리드 경로에서는 쓰지 않는다.

### 4.2 컴포넌트별 소비 방식

| 컴포넌트                                            | 소비 방식                                       |
| ----------------------------------------------- | ------------------------------------------- |
| `WidgetGridCardContent`                         | `displayItems`를 props로 전달만. parseType 분기 없음 |
| `SensorGauge` / `ChainedGauge`                  | 계산 없이 표시만                                   |
| `SensorListGauge`                               | `displayItems` 행 렌더                         |
| `SensorValueBarChart` / `SensorStackedBarChart` | item의 `value` + `threshold`                 |
| `LowFrequencyDashboardChart`                    | item의 `series`                              |

### 4.3 소켓

* 실시간 값은 `useWidgetGridCardData`(`gauge-sensor-data` 구독 + `buildWidgetGridCardDataWithRealtime`)에서 range와 합류된다.
* 컴포넌트는 소켓을 직접 구독하지 않고 데이터층 합류값만 쓴다. 뷰 계층에 신규 구독을 추가하지 않는다.

***

## 5. 구현 시 주의사항

1. parseType 분기 추가는 `displayItems` 생성기에만 한다. 컴포넌트로 새어 나가지 않게 한다.
2. GDMS 축별 총합 item은 `deviceId` / `channel` / `dataKey`가 없다. `key`·`groupKey` 설계가 필수다.
3. 게이지 컴포넌트는 레거시 센서보드와 공유된다. 시그니처를 바꿀 때 레거시 경로 영향 범위를 함께 확인한다.
